# ADR 0049: UI-Sprache — Message-Kataloge de/en, Locale-Formatierung

**Status:** Akzeptiert (2026-11-19) — umgesetzt (Message-Kataloge, Intl-Formatierung, Playwright-Tests); Vorgeschlagen 2026-11-03
**Baut auf:** ADR 0030 (Auth/Rollen, UI-Grundgerüst). Teil 2 von Issue #168; löst Issue #370.

## Kontext

Die fabrikant-UI (`web/`, Vanilla JS ohne Build) hatte alle UI-Strings hartkodiert
(Deutsch) und das Locale `de-DE` für Uhr/Datum. Issue #370 verlangt eine
Sprachumschaltung de/en für die **UI-Chrome** (Labels, Buttons, Hinweise,
Filter, Badges). User-Content — Specs, Prompts, Logs, Chat-Antworten,
Run-Records — bleibt in der Sprache, in der er erzeugt wurde, und wird
**nicht** übersetzt.

## Entscheidung

1. **Kataloge als statisches JSON:** `web/i18n/de.json` und `web/i18n/en.json`
   mit identischem Key-Satz. Der Server liefert sie über die bestehende
   Static-Route (`_static` → `WEB_DIR`), es gibt keine neue API und keinen
   Build-Schritt.
2. **Kein Framework:** Ein kleiner i18n-Modul-Block in `app.js` (kein
   Import, kein Bundler): `t(key, vars)` mit `{Platzhalter}`-Substitution und
   definiertem Fallback (aktive Sprache → `en` → der Key selbst),
   `i18nResolve()` (localStorage `fabrikant.lang` > `navigator.language` >
   `en`), `i18nLoad()` (beide Kataloge per `fetch`), `i18nApply()`
   (setzt `<html lang>`, `document.title`, alle `[data-i18n]`/
   `[data-i18n-ph]`/`[data-i18n-title]`-Elemente und rendert die dynamischen
   Views neu), `setLang()`/`toggleLang()`.
3. **Statische Strings** in `index.html` tragen `data-i18n*`-Attribute; der
   HTML-Default bleibt Deutsch (No-JS-Fallback), JS wendet die aufgelöste
   Sprache beim Load an.
4. **Umschalter im Header** der Basis-View (`#langtoggle`, de ↔ en); die
   Wahl wird in `localStorage` persistiert und überlebt Reloads.
5. **Locale-Formatierung:** Datum/Zeit über `Intl` (`fmtDateTime`) mit der
   gewählten Sprache; kein hartkodiertes `de-DE` mehr (CI-Test).
6. **Tests:** Statische Tests prüfen Key-Parität de/en, dass jeder
   `t("…")`-Key in `app.js` und jedes `data-i18n*`-Attribut in `index.html`
   in beiden Katalogen existiert, dass keine ungenutzten Keys und kein
   `de-DE` in `web/` vorkommen, und dass der Server die Kataloge liefert.
   Ein Playwright-Test lädt die UI mit de- und en-Browser-Sprache und prüft
   `<html lang>`, Beispiel-Texte, Toggle + Persistenz.

## Konsequenzen

- Jeder neue UI-String braucht einen Eintrag in **beiden** Katalogen
   (CI-Test blockiert Abweichungen).
- Ein Sprachwechsel rendert die offenen Views neu; die Run-Historie wird
   dabei zurückgesetzt (bewusste Aktion, akzeptabler Trade-off).
- Bestehende Chat-Log-Zeilen werden beim Sprachwechsel nicht nachträglich
   übersetzt (Content, nicht Chrome).
- `t` ist jetzt eine globale Funktion in `app.js`; Pfeil-Parameter mit dem
   Namen `t` shadowen sie (in den betroffenen Maps auf `tr`/`trimmed`
   umbenannt).
